# Правила работы Codex

1. Перед работой прочитай Issue целиком, комментарии, README.md и документы docs/PRD.md, docs/ARCHITECTURE.md, docs/DESIGN.md, docs/DECISIONS.md. Если требования противоречат друг другу, задай вопрос владельцу.
2. Выполняй только scope текущего Issue. Для Issue #1 разрешены только документация и инструкции: без приложения, зависимостей, UI-кода, инфраструктуры и фиктивных тестов.
3. Различай утверждённые решения, предложения и открытые вопросы. Не выдавай предположения, предварительный стек или дизайн за утверждённые решения. Недостающие сведения запиши как вопросы.
4. Для будущего кода добавляй содержательные тесты поведения, включая серверные права доступа и граничные состояния времени. Выполняй подходящие проверки и честно сообщай о непройденных и незапущенных проверках. Для документации проверяй ссылки и согласованность; не создавай тесты-заглушки.
5. Используй только вымышленные данные. Не коммить ключи, пароли, секреты и реальные персональные данные; не записывай их в промпты, логи и скриншоты. Будущие пароли хешируй, секреты храни безопасно вне Git.
6. Работай в отдельной ветке существующего checkout. Среда уже изолирована: не создавай worktree без явного запроса. Не меняй main напрямую. Сохраняй чужие изменения.
7. Процесс: GitHub Issue → Codex → тесты/проверки → Pull Request → ручное утверждение владельцем. Для Issue #1 создай Draft PR. Никогда не выполняй merge автоматически и не включай auto-merge. Публикация PR не означает одобрение решений.
8. Поддерживай согласованность документов и журнал решений. Фиксируй использование ИИ по шаблону docs/AI_LOG.md без выдуманных результатов, моделей и вклада человека.

## CI документации

Для Issue #3 разрешены workflow и вспомогательный скрипт проверки документации. Перед PR запускай `python3 scripts/check_docs.py` из корня и `git diff --check`. Скрипт проверяет отслеживаемые Git Markdown-файлы: обязательные документы, UTF-8, относительные ссылки и базовое форматирование; новые файлы сначала добавь через `git add`.

Workflow `.github/workflows/docs-ci.yml` запускает `Documentation checks` для PR в main и push в main, с `contents: read`, без секретов, записи в репозиторий и деплоя. Actions закрепляются полным SHA; зависимости Python не устанавливаются. Не заменяй этим CI будущие проверки Node/TypeScript/build/Playwright: они добавляются отдельным Issue после согласования стека и появления приложения. Не объявляй удалённый CI успешным без результата Actions; при блокировке укажи точную причину.

Порядок: подготовка VPS (#24 / merged #26) → последний отдельный фундамент (#27) → законченные пользовательские вертикали (расписание и staff CRUD структуры, успеваемость, заявки/справки, уведомления) → полная MVP/UX/конкурсная приёмка → отдельно разрешённое владельцем защищённое развёртывание → необязательные дополнения. Фундамент не означает готовый MVP. Следующий scope задаётся отдельной согласованной Issue, без ещё одной задачи модернизации фундамента и без преждевременных таблиц/заглушек.

В рамках согласованной Issue самостоятельно закрывай подтверждённые блокеры и повторяй проверки до зелёного CI. Косметику и малосущественные оптимизации записывай в Deferred, не задерживая функции. Эскалация нужна при архитектурном/продуктовом противоречии, риске данных/прав или выходе за scope. Используй [audit](docs/FOUNDATION_AUDIT.md) и [feature handoff](docs/FEATURE_HANDOFF.md).

GO FOR FEATURE DEVELOPMENT не является production GO. Vendor-unfixed HIGH и dev-only moderate не блокируют функциональную разработку, но pre-deploy security gate D остаётся NO-GO без отдельного review. Нельзя скрывать находки ignore-правилами. Сохраняй standalone, Functions/Neon и VPS-путь. Только один Draft PR, ручной merge владельца; без deploy, покупки, registry dispatch, облачных ресурсов, настоящих секретов и push в main.
