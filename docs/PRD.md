# PRD: конкурсный MVP

Статус: требования из [Issue #1](https://github.com/bam-low/mgimo/issues/1) с уточнениями из [ревью владельца](https://github.com/bam-low/mgimo/pull/2#pullrequestreview-5773081368). Журнал статусов — [DECISIONS.md](DECISIONS.md). Детали, которых нет в Issue, требуют согласования.

## Цель

Создать работающий конкурсный прототип «Цифровой деканат будущего», демонстрирующий повседневные задачи студента и деканата. Использовать исключительно вымышленные данные и явное обозначение «концепт, не официальный сервис». Текущий этап — планирование, не реализация.

## Роли и обязательные сценарии

| Роль | Сценарии |
| --- | --- |
| Студент | Регистрация/вход; выбор факультета → направления → группы; просмотр профиля; расписание на сегодня и неделю; оценки и зачёты; заявки и их статусы; уведомления. |
| Сотрудник деканата | Создание и управление факультетами, направлениями и группами; управление групповым расписанием; обработка заявок и изменение их статуса. |

Расписание принадлежит группе. Студент получает его через свою связь с группой; копий расписания в записи студента нет.

## Главная студента

Показать все пары сегодня с временем. Текущую пару выделять по реальному времени с учётом часового пояса университета; при необходимости показывать прогресс. Предусмотреть состояния «до пар», «перемена», «все пары закончились», «сегодня пар нет». Устройство пользователя может находиться в другом часовом поясе.

## Границы MVP и качество

- Один демонстрационный вымышленный вуз. Несколько вузов учитываются структурно, без реализации multi-tenant SaaS.
- Минимум два демонстрационных студента с различными данными и один сотрудник.
- Серверная проверка прав, хеширование паролей, безопасное хранение секретов.
- Дизайн приоритетен: mobile-first от 360 px, сначала сравнить три разные авторские концепции; выбранной концепции пока нет.
- Прототип и все его ресурсы должны быть доступны из РФ без VPN.
- Конкурсные материалы готовятся отдельной частью работы; обязательный состав отчёта указан ниже.

## Конкурсные материалы

Состав уточнён владельцем в [ревью PR #2](https://github.com/bam-low/mgimo/pull/2#pullrequestreview-5773081368) на основании конкурсного ТЗ. Обязательный отчёт включает:

- описание проблемы и пользовательских сценариев;
- полный перечень использованных ИИ-инструментов, IDE и сервисов;
- ключевые промпты и диалоги;
- скриншоты удачных и неудачных итераций;
- объяснение реализации входа, базы данных и безопасности;
- описание этапов, выполненных вручную, и вклада человека.

Видео длительностью до 5 минут — опционально.

Из переданного владельцем ТЗ известны начало подачи **8 ноября в 19:00 МСК** и объявление итогов **28 ноября**. Дата и время закрытия подачи не указаны и остаются открытым вопросом; их нельзя выводить из даты объявления итогов. Требования к формату отчёта и остальные неуказанные детали необходимо уточнить.

## Критерии приёмки будущего прототипа

| Проверка | Ожидаемый результат |
| --- | --- |
| Регистрация и вход | Можно войти и выбрать существующую цепочку факультет → направление → группа; выбор соответствует структуре вуза. Детали регистрации подлежат согласованию. |
| Два студента | Различающиеся профиль, успеваемость и заявки отображаются для соответствующего аккаунта; чужие данные недоступны. |
| Расписание | Сегодня и неделя соответствуют группе; изменение сотрудником группового расписания отражается у связанных студентов без копирования в их записи. |
| Время | Проверены начало и конец пары, перемена, время до первой/после последней пары, день без занятий и смена календарного дня в часовом поясе вуза; выделение обновляется без повторного входа. |
| Успеваемость | Студент видит свои оценки и зачёты; шкалы и источник данных предварительно согласованы. |
| Заявки и уведомления | Студент создаёт заявку и видит её статус, сотрудник обрабатывает её и меняет статус; студент видит свои уведомления. Типы, переходы и триггеры согласованы до реализации. |
| Управление структурой | Сотрудник может создавать и управлять факультетами, направлениями, группами и их расписанием. Правила удаления связанных данных согласованы. |
| Права и секреты | Прямые серверные запросы студента к функциям сотрудника и чужим данным отклоняются; пароли не хранятся открытым текстом, секретов в Git нет. |
| Дизайн | Три авторские концепции сравнены, выбор явно утверждён владельцем; выбранный интерфейс проверен от 360 px. |
| Доступность из РФ | На целевой площадке из РФ без VPN проверены вход, основные сценарии и загрузка всех ресурсов, включая шрифты и изображения. Метод и результаты документированы. |
| Демонстрация | Есть минимум два разных студента и сотрудник; все данные вымышлены, обозначение неофициального концепта заметно. |

Эти проверки — требования к будущей реализации, они сейчас не выполнялись. Приёмка текущего документационного этапа: семь согласованных файлов, явные статусы решений, список вопросов в Draft PR, отсутствие кода/зависимостей/секретов и отсутствие merge.

## Non-goals

Встроенный GPT/ИИ-помощник; официальный университетский сервис; реальные персональные данные; multi-tenant SaaS. Интеграции с реальными системами, производственная эксплуатация и дополнительные роли не входят в утверждённый scope и требуют отдельного решения. Issue #1 не включает создание приложения, установку зависимостей и изменение инфраструктуры.
