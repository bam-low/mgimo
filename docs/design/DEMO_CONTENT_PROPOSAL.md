# PROPOSED — отдельное улучшение демонстрационного наполнения

Основание: [Issue #34, дизайн-ревью07.11.2026](https://github.com/bam-low/mgimo/issues/34). **Только предложение для владельца, не реализовано и не разрешает изменение данных.** В текущем UI PR seed, миграции, пользовательские записи, пароли, роли и расписание существующей БД не меняются. Длинные названия в Playwright — новые fixtures только отдельной *_test DB, не новое конкурсное наполнение.

## Предлагаемый набор

- Две различимые вымышленные группы: «ОИ-26-01» и «ПК-26-02»; факультет «Общественные исследования», направление «Социальные процессы и коммуникации». Это примеры содержимого, не утверждённое название демо-вуза.
- Нейтральные дисциплины: «Академическое письмо», «Основы исследовательской работы», «Практикум по анализу данных». Имена преподавателей — явно созданные персонажи, например «Мира Ветролесьева», «Никита Сказореченский», без заимствования реальных ФИО. Утверждение имён и пометка вымышленности — отдельно владельцем.
- Несколько занятий с интервалом/переменой, короткий день и полностью свободный день; у второй группы другое расписание. Часть достаточно длинных названий нужна для проверки переноса, но технические суффиксы не должны быть обычным конкурсным содержимым.
- Сохранить маркировку концепта и synthetic-only регистрацию. Естественные названия не являются разрешением настоящих персональных данных, расширенных справочников, рейтингов или новых модулей.

## Безопасный порядок отдельной задачи

1. Владелец отдельно утверждает тексты и момент календарной демонстрации. Датированные занятия не становятся recurrence/автоматическим переносом недели; смена этой бизнес-модели здесь не предлагается.
2. Подготовить отдельный content PR. Предпочтительный проверяемый вариант — первоначальное наполнение **новой выделенной synthetic DB**, без подключения к существующей пользовательской/production БД. Создание такой БД и публикация потребуют отдельного разрешения; этот документ их не даёт.
3. Если нужен вариант с существующей demo DB, сначала отдельный план добавления через штатные операции STAFF и ревью владельца. Не удалять/обновлять старые записи, не сбрасывать seed, credentials, роли, membership или историю. Никаких скрытых upsert repair, TRUNCATE, миграций схемы или расписания «относительно каждого запуска».
4. Проверить аудит, права групп, идемпотентность первоначального наполнения, день с несколькими парами/переменой/без пар и ручную демонстрацию. До утверждения ничего из предложения не выполняется.

Текущие UI-регрессии используют существующий seed без его изменения; отдельный clock fixture проверяет UI-состояния, не передвигая часы сервера и не меняя данные БД. Production NO-GO сохраняется.
