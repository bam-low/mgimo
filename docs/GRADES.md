# Успеваемость — Issue #39

[Утверждённая Issue #39](https://github.com/bam-low/mgimo/issues/39) задаёт более позднее решение: STUDENT читает собственные результаты, APPROVED STAFF управляет результатами своего вуза. Документ описывает реализацию в функциональной ветке; до ручного merge это не состояние main. Проверки и точный SHA фиксируются в Draft PR. Production NO-GO сохраняется.

## Данные и права

Subject — вузовская дисциплина, name/active/version. STAFF создаёт, переименовывает, деактивирует и восстанавливает; справочник не связан автоматически с ScheduleEntry.title. Grade принадлежит UniversityMembership и Subject одного вуза: составные внешние ключи запрещают межвузовские комбинации. Перевод не перепривязывает личную историю к новой группе. CASCADE DELETE для результатов отсутствует.

Результат имеет kind MARK с целым mark 2–5 либо CREDIT с credit PASSED/FAILED; другое поле NULL. Эти инварианты проверяют строгий Zod и SQL CHECK. issuedOn — календарная дата вуза 2000–2100, PostgreSQL DATE без преобразования в зону устройства. authorId — первоначальный автор, updatedAt/version — технические поля; автор исправления записан в неизменяемом AuditLog. Несколько результатов по одной дисциплине допустимы. Периоды, семестры, GPA и итоговые ведомости не вводятся.

| Операция | STUDENT | STAFF своего вуза |
| --- | --- | --- |
| Чтение результатов | Только собственное членство, APPROVED и активная цепочка прикрепления | История выбранного студента, включая аннулированное |
| Создание/исправление/аннулирование | Запрещено | Повторная проверка STAFF и активного прикрепления выбранного студента в транзакции |
| Новая запись/исправление | Запрещено | Только активная дисциплина своего вуза |
| Справочник дисциплин | Нет отдельного управления | Создание, переименование, active/version |

PENDING/REJECTED/отзыв/неактивная ветка закрывают учебное чтение и запись. Деактивация дисциплины сохраняет историческое чтение. Аннулирование — voided=true, без физического DELETE и без восстановления через UI.

## API и атомарность

- `POST /api/staff/subjects`: CREATE(operationId UUID,name) либо EDIT(id,version,name,active).
- `POST /api/staff/grades`: CREATE(operationId UUID,membershipId,subjectId,issuedOn,result), EDIT(id,version,subjectId,issuedOn,result,reason), VOID(id,version,reason). result — строгий объект `{kind:"MARK",mark:5}` либо `{kind:"CREDIT",credit:"PASSED"}`. Причина исправления/аннулирования обязательна, 1–500 символов.
- `GET /api/grades`: студенту своё; STAFF передаёт membershipId. cursor scoped по выбранному студенту, чужой cursor →404. Минимальные DTO, private/no-store, без auth/session/email. Списки по 25+1 со стабильным порядком issuedOn/id; roster по id.

Повтор CREATE с тем же operationId безопасно даёт 409; при неопределённом сетевом исходе интерфейс сохраняет operationId. EDIT/VOID проверяют version под блокировкой, параллельный повтор →409. Изменения и AuditLog коммитятся вместе, отказ аудита откатывает запись. Блокировки: membership row → university advisory lock, тот же порядок, что у переводов; STAFF и состояние перечитываются после блокировки. Subject использует university lock. Существующие auth/CSP/cookies и регистрация не меняются.

AuditLog.reason содержит JSON с membershipId, причиной и before/after значениями результата; actorId/universityId/targetId/action/createdAt используют существующую схему. Секретов и лишних профилей там нет. STAFF видит аудит выбранных результатов; страница показывает по 100 событий с отдельной scoped cursor-пагинацией auditCursor. Полный неизменяемый аудит сохраняется в БД и доступен постранично. Справочник ограничен 200 дисциплинами: превышение явно отклоняется, не обрезается молча.

Migration `20261107120000_grades` additive: Subject/Grade, необходимые ключи/индексы/CHECK; учётки, пароли, роли, прикрепления и расписание не изменяются. Runtime grants для обеих новых таблиц только SELECT/INSERT/UPDATE, без DELETE/DDL/TRUNCATE. Seed не создаёт оценок: источник исключительно действие STAFF; тесты используют отдельную *_test БД и вымышленные записи.

## Исправление даты расписания

В baseline `ScheduleField` устанавливал custom validity в passive effect. В браузере воспроизведён промежуток: input уже содержит 31.02.2026, checkValidity ещё true; после effect false. Поэтому одиночный снимок валидности в E2E зависел от планировщика. В обработчике ввода проверка теперь синхронная, изменение source синхронизируется layout effect до отрисовки. Парсинг сохраняет строгую календарную проверку; невалидное значение не остаётся прежней валидной датой controlled callback. Регрессия проверяет отсутствие POST при попытке сохранения и сообщение валидации, затем успешный настоящий сценарий. Прямой API с 2026-02-31 возвращает 400.

## Ручная приёмка и проверки

1. STAFF: «Успеваемость» → справочник → создать вымышленную дисциплину; при необходимости фильтр группы → выбрать студента по имени/группе → выставить 5 и «Зачтено» отдельными записями.
2. STUDENT: собственные дисциплина/дата/значения, без редактирования. Другой студент не получает записи через URL/API.
3. STAFF исправляет 5 на 4 с причиной и подтверждением; затем аннулирует. Студент видит только действующие результаты, сотрудник — историю before/after и причины.
4. Перевод сохраняет оценки; отзыв закрывает доступ, история остаётся. Неактивная дисциплина не допускает новых оценок и сохраняет прежние.
5. Проверить 360/390/1280, длинные названия, keyboard/focus, reduced motion, пустые состояния. Не использовать настоящие данные.

Тесты: `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run test:integration`, schema diff, standalone build/runtime/E2E, Functions build/runtime/E2E/cold start и VPS rehearsal. `tests/grades.test.ts` проверяет реальные handlers/SQL/транзакции; limited-role probe и negative grants охватывают новые таблицы; общий `tests/e2e/grades.spec.ts` входит во все три runtime-пути и сохраняет реальные screenshots в test-results. Документация — `python3 scripts/check_docs.py` после git add. Не считать незапущенные/непрошедшие проверки успешными.

Реальные host/TLS/ingress/РФ/offsite restore, vendor-unfixed HIGH, мобильные устройства и полный WCAG остаются отдельными gates. После ручного merge следующие вертикали: заявки/справки → уведомления; без автоматического deploy/merge.
