# Передача проекта «Кампус»

Документ для человека, который продолжит проект после конкурса вместе с ИИ-ассистентом (Claude Code, Codex или похожим). Прочитайте его целиком перед первым изменением.

## 1. Что передаётся и где оно работает

- **Код** — этот репозиторий (`main`). Всё рабочее состояние в нём; ветки задач сливаются через Pull Request.
- **Стенд** — VPS Debian 13 (Fatmetal), домен `213-109-106-89.fatmetal.net`, HTTPS через Let's Encrypt. Приложение, инструменты миграций и PostgreSQL 17 — отдельные контейнеры проекта Docker Compose `campus`; данные — том `campus_pgdata`. Текущий выпуск: каталог `/opt/campus/current` → `/opt/campus/releases/<SHA>`, ID образов — в `/etc/campus/release.env`.
- **Данные** — только вымышленные: один демо-вуз, два студента, один сотрудник.

## 2. Что передать лично (никогда не через репозиторий и чаты)

| Что | Где хранится | Зачем |
| --- | --- | --- |
| Доступ к GitHub-репозиторию | Настройки репозитория → Collaborators | Ветки, PR, Codespaces |
| SSH-ключ и пароль `sudo` пользователя `campus-admin` | У владельца | Все операции на VPS |
| Ключ подписи выпусков (`campus_release`) | У владельца; публичная часть — `/etc/campus/allowed_signers` на VPS | VPS принимает только подписанные пакеты |
| Ключ расшифровки резервных копий (age) | У владельца; публичный получатель — `/etc/campus/backup-recipients.txt` | Проверка и восстановление копий БД |
| Секреты стенда | `/etc/campus/secrets` на VPS (пароли ролей БД, сертификаты БД, секрет сессий) | Работа приложения; не копировать никуда |
| Пароли демо-аккаунтов | Студенческие — в README; пароль сотрудника — у владельца | Вход на стенд |

При смене владельца рекомендуется выпустить новый ключ подписи и заменить `allowed_signers`, сменить пароли демо-аккаунтов скриптом `ops/vps/demo-reset.mjs passwords` и пароль `sudo`.

## 4. Правила работы

Полностью — в [AGENTS.md](../AGENTS.md). Коротко:

1. Каждая задача — отдельная ветка от `main` и Pull Request. ИИ не сливает PR и не включает auto-merge: это делает человек после проверки.
2. Изменение поведения — вместе с тестом: права доступа, чужие данные, граничные состояния времени. Ошибку не «чинят» удалением теста или ослаблением проверки.
3. Только вымышленные данные. Никаких ключей, паролей и персональных данных в коммитах, логах, скриншотах и промптах.
4. Новая таблица в БД = миграция + запись в `ops/vps/migration-contract.json` + права в `scripts/launch-db-policy.mjs` + тест прав. Иначе выпуск на VPS не пройдёт проверки.
5. Тексты кнопок и подписи полей, на которые опираются E2E-тесты, меняются только вместе с тестами.
6. Каждый экран проверяется на 360 и 1280 px; удобство на телефоне — приоритет.

## 5. Первый запуск

1. Локально: [инструкция локального демо](LOCAL_DEMO.md) (Docker + PostgreSQL на loopback + `npm ci` + миграции + seed + `next dev`).
2. Тесты: `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run test:integration` (нужна отдельная БД с суффиксом `_test`).
3. Полный E2E и сборка образов — только в Linux (GitHub Actions или Codespaces), см. раздел 7.

## 6. Как начать сессию с ИИ

Дайте ассистенту доступ к локальной копии репозитория и начните с такого запроса:

```text
Ты продолжаешь проект «Кампус» (демо цифрового деканата). Прочитай AGENTS.md, README.md,
docs/HANDOFF.md, docs/ARCHITECTURE.md и docs/DECISIONS.md. Затем кратко перескажи, как устроены роли, проверки
доступа и выпуск на VPS, и предложи план задачи: <опишите задачу>. Работай в отдельной ветке,
пиши тесты на права доступа, проверяй экраны на 360 и 1280 px, ничего не сливай в main сам.
```

Хорошая практика: одна задача — одна сессия и один PR; просить ассистента сначала план и оценку, потом код; после изменений просить прогнать lint, типы, unit и интеграционные тесты и честно перечислить, что не запускалось.

## 7. Выпуск на VPS

GitHub Actions собирает и проверяет выпуск (`.github/workflows/vps-ci.yml`). Если Actions недоступны, тот же процесс выполняется вручную в Codespaces:

1. **Сборка (Codespaces).** Снять ACL по умолчанию с `/tmp` (`sudo setfacl -k /tmp`) **до** создания копии; запустить `dockerd` с `overlay2` и data-root в `/tmp` (иначе ID образов не совпадут с архивом); чистая копия точного SHA `main` через `git worktree`; `npm ci`, проверки, сборка трёх образов, `prepare-vps-baseline` + `test-vps` (полный E2E) + репетиция обновления, Trivy (блокируют CRITICAL и исправимые HIGH; ignore-правила запрещены), упаковка `scripts/package-vps-release.sh`, ZIP.
2. **Подпись (у владельца).** Сверить SHA-256 ZIP и `SHA256SUMS`, подписать `ssh-keygen -Y sign -n campus-vps-release`.
3. **Доставка.** Одним `scp -r` пакет и три проверочных скрипта, взятых из коммита через `git show` (не из рабочей копии Windows — там CRLF).
4. **VPS.** `verify-delivery.sh` (подпись) → новый каталог релиза и env рядом со старым → остановка приложения и зашифрованная копия БД (проверить расшифровку!) → новый образ БД на том же томе, `admin.mjs migrate/grant/check` → запуск приложения и ручная приёмка → переключение `current` и `release.env`. Старый каталог и env сохраняются для отката.

Подробно: [обновление VPS и откат](VPS_UPDATE_RUNBOOK.md), [первое развёртывание](VPS_DEPLOY_RUNBOOK.md), [архитектура VPS](VPS_ARCHITECTURE.md).

**Служебные операции владельца** (через контейнер инструментов, только с `--owner-approved`):

```bash
# из каталога текущего выпуска на VPS, под root
dc() { docker compose -p campus --profile ops --env-file /etc/campus/release.env -f ops/vps/compose.yaml run --rm --no-deps -T tools "$@"; }
dc node ops/vps/demo-reset.mjs preview --owner-approved            # что будет удалено, код подтверждения
dc node ops/vps/demo-reset.mjs apply --owner-approved --confirm CODE  # очистка демо одной транзакцией
printf '%s\n' 'пароль-сотрудника' 'пароль-студента-1' 'пароль-студента-2' | dc node ops/vps/demo-reset.mjs passwords --owner-approved
```

Перед `apply` обязательно сделайте свежую резервную копию (`ops/vps/backup.sh`).

## 8. Подводные камни

- **Windows и переводы строк.** Рабочая копия на Windows хранит файлы с CRLF; миграции закреплены правилом LF в `.gitattributes`. Скрипты для VPS берите из коммита (`git show`).
- **Лимит входа.** 10 попыток на логин за 15 минут; автоматические проверки легко его исчерпывают.
- **После `prisma generate`** перезапустите dev-сервер — иначе он работает со старым клиентом БД.
- **Тестовая БД** обязана иметь имя с суффиксом `_test`; тесты на одной и той же БД накапливают данные — при странных конфликтах пересоздайте её.
- **Стили.** Правьте `design.css`; `!important` внутри legacy-слоёв перебить нельзя — такие места правятся в самих legacy-файлах.
- **Nginx.** Общий лимит тела запроса 16 КБ; для загрузки документов, портфолио (`= /api/portfolio`, 3136 КБ) и импорта расписания есть отдельные участки с бо́льшим лимитом. После выпуска с новым участком конфигурацию Nginx нужно перегенерировать (`render_nginx.py --public`) и перезагрузить — иначе загрузка PDF получит 413.
- **Напоминания о дедлайнах** создаются при обращении студента к кабинету (счётчик колокольчика, главная), а не планировщиком: студент, который не заходит, увидит напоминание при следующем входе.
- **Codespaces.** ACL `/tmp` может вернуться в процессе сборки — проверяйте перед упаковкой (`getfacl -p /tmp`).

## 9. Открытые задачи

- **Справочник**: разделы справочной информации для всего вуза или группы (текст и PDF; хранение файлов — как в заявках).
- Рекомендации финального аудита (21.11.2026): HSTS, таймеры резервного копирования и очистки на VPS, уведомление студентов при удалении расписания, редактирование объявлений, автоматический список студентов в «Успеваемости», сворачивание форм структуры на телефоне. Пароль сотрудника не публиковать: с ним можно менять демо-данные.
- Пересобрать образы, когда в Debian выйдет исправление `libssl3t64`.
- Отдельная репетиция обновления «от установленного выпуска» (сейчас репетиция идёт от исторической базы `287912fe`).
