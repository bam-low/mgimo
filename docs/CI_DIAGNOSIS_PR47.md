# PR #47: диагностика входа и native validationMessage

Дата: 13.11.2026. Исходный HEAD: `dcdafe48cee4d4d1f2e7d7359046bd69a017c6b3`; main: `f375bee1e329f61200bbafebf34c80bed805c8b1`. Документ содержит результаты и предложения **на согласование**, без изменения auth/security и тестовой инфраструктуры в репозитории.

## Краткий вывод

Подтверждён воспроизводимый отказ **HTTP 429 по общему лимиту источника**: 21-й вход в минутном окне при восьми входах данного аккаунта. Набор E2E выполняет 20 входов до теста schedule-states, который пытается войти ещё раз. Его ожидание `/cabinet` маскирует первичный отказ в виде ошибки навигации.

Нельзя восстановить HTTP-статус каждого исторического GitHub-запроса: старые логи не записывали его. Подтверждены механизм отказа и воспроизведение 429 в том же тесте локально. Текущий VPS-диагностический повтор прошёл; это не доказательство случайности прежнего отказа и не исправление бюджета.

Для даты подтверждён отдельный режим: до готовности клиентского JS отсутствует custom validity, а форма может сделать нативный GET. После готовности та же невозможная дата корректно отклоняется. Связь этого режима с конкретным старым VPS-runner не доказана: в его логе нет значений поля и состояния гидратации.

## Безопасный сбор доказательств

Использованы временные копии тестов/наблюдатели вне Git, настоящие Next.js/Functions/Chromium/PostgreSQL и закрытая локальная VPS-репетиция. Обработчики, auth-политика, API и проверки тестов не заменялись. Записывались только роль вымышленного пользователя, статус, разрешённый код ошибки и числовые счётчики. Пароли, cookies, токены, HMAC-ключи, request/response payload и storageState не публикуются. Диагностические failure-context с формами отключены, trace/HAR не велись. В первом измерении наблюдатель задержал снятие счётчиков при отказе; поздний снимок исключён из доказательства порога. Полный инструментированный запуск не объявляется точным воспроизведением таймингов GitHub.

## 1. HTTP, код ошибки и отказ на /login

Контроль проведён на новой `campus_pr47_quota_test`, неизменённом production-приложении и настоящих часах. Входы выполнены в одном реальном минутном окне, без изменения Date, очистки RateBucket, обхода CSRF или подмены IP. Использованы три настоящих вымышленных seed-пользователя: 8 входов студента 1, 8 сотрудника, 4 студента 2.

| Шаг | HTTP | Общий счётчик | Счётчик студента 1 за 15 минут |
| --- | --- | --- | --- |
| Первые 20 запросов | Каждый 200 | 20 | 8 |
| 21-й запрос студента 1 | **429** | **21** | **8**, не увеличился |
| Первый запрос этого же студента после перехода в Functions | 200 | 1 для другого источника | 1 для другого источника |

Отдельного поля `code` в JSON отказа нет: фактическое значение `null`, не выдуманный `RATE_LIMITED`. Публичный wrapper возвращает общее сообщение Denied. Код проверен чтением [auth route](../src/app/api/auth/[...all]/route.ts), [security](../src/server/security.ts) и [errors](../src/server/errors.ts): сначала проверяется общий источник, затем аккаунт. Better Auth internal rateLimit отключён; действуют внешние серверные ограничения 20/мин и 10/15 мин. Ошибка пароля вернула бы 401, а не этот 429.

После 429 ранее полученная сессия студента сохранила доступ к своей группе (200); чужая группа и STAFF endpoint дали 403, сотрудник получил 200. Это исключает потерю PostgreSQL/всех сессий или ослабление прав как объяснение контрольного отказа.

В обычном диагностическом standalone-наборе также получен 429 в schedule-states. В Functions-повторе та же последовательность пересекла минутную границу: после первых 20 входов счётчик нового окна был 0, запрос schedule-states стал первым и получил 200. Это наблюдаемый механизм зависимости от времени, а не заявление о «случайном CI».

AuthForm при 429 показывает сообщение лимита и не выполняет router.push. Тест ждёт только URL, поэтому первичная ошибка превращается через 5 секунд в `expected /cabinet, received /login`. Увеличение timeout не устраняет отказ: успешного входа не было.

## 3. Пользователи, сессии, PostgreSQL и RateBucket

- Внутри runtime тесты идут одним worker, browser context создаётся отдельно; одни и те же три seed-аккаунта используются разными сценариями. Новые регистрируемые персонажи действительно отдельные. Закрытие context не отзывает серверную сессию. Logout отзывает соответствующую реальную сессию.
- Существующий session-cache сохраняет только настоящие UI-cookies, приватно, проверяет защищённый API и отклоняет отозванную сессию. Кэш создаётся заново каждым Playwright globalSetup и удаляется после runtime. Foundation/journey намеренно проверяют входы/выходы; их нельзя молча пропускать.
- Node CI использует одну БД для integration, standalone и Functions. Seed выполняется до них, не является сбросом RateBucket и не сбрасывает чужие права/пароли. Integration использует отдельные тестовые источники; auth-код не перенесён в другой процесс или БД между двумя E2E-runtime.
- Источники различаются: standalone без trusted header использует `local-demo`, Functions harness — переписанный `x-vercel-forwarded-for` с loopback. HMAC-ключи различны. Общая БД **не означает общий login bucket между этими двумя runtime**. Наблюдаемый отказ возникает уже внутри одного runtime.
- Контроль: перед переключением runtime в той же БД было 3 пользователя/20 сессий/5 buckets; после первого Functions-входа — 3/21/7. Старые данные не очищались, источник Functions начал с 1. В точке начала обычного Functions-набора также сохранились пользователи, сессии и buckets прежнего runtime; его source counter был 0.
- VPS — отдельный Docker project, отдельная новая PostgreSQL, случайные тестовые секреты и seed дважды; он не использует БД Node CI. Один gateway даёт тестам общий источник. В локальном повторе все наблюдавшиеся sign-in получили 200, 16 E2E и encrypted fresh restore прошли. Это показывает работоспособность пути, но не меняет лимиты и не опровергает измеренный бюджет.

Локальный Functions router дополнен обработкой сгенерированного 404 rewrite; sign-in и security gates этим не менялись. Идентичный auth-код защищает main и PR.

Дополнительный рендеринг/проверки меняют длительность сценариев и расположение запросов относительно фиксированных окон. Это может менять место отказа, но не является новой политикой авторизации.

## 5. Отдельная проверка невозможной даты

Сначала при уже готовом JS в прямом контрольном повторе 20/20 вводов с CPU throttling 6× сохраняли сообщение ошибки. В текущих диагностических Functions/VPS сценариях проверка даты также прошла.

Дополнительно задержаны **настоящие** JS chunks на чистой странице; API не подменялись. До их загрузки: видимый текст `31.02.2026`, скрытое canonical значение ещё `2026-11-16`, `validationMessage` пуст, `checkValidity()` true. Нажатие отправки произвело нативную GET-навигацию. После загрузки JS тот же ввод дал canonical `""`, русское сообщение и `checkValidity()` false. Список ID занятий до/после совпал: мутаций не было. Это клиентская готовность/сохранение ввода, серверный парсер не ослаблялся.

Режим воспроизведён детерминированно, но без старого DOM/event trace нельзя честно доказать, что именно он произошёл в GitHub. В диагнозе оставляется этот предел, а не приписывается неизвестному событию причина.

## 6. Минимальные исправления — только после согласования

### Предложение A: тестовые входы, без production-изменений

1. В `grades.spec.ts` перед новым входом использовать уже существующий `reuseSession` для трёх seed-аккаунтов; он проверяет protected API и настоящее право. Успешную новую сессию по-прежнему запоминать через `rememberSession`.
2. В `schedule-states.spec.ts` использовать тот же путь: предмет теста — расписание, отдельный повторный вход не является проверяемой функцией. Если сохранённая сессия отсутствует/отозвана — настоящий UI-вход.
3. При фактическом входе использовать `.fill()` и явно дождаться POST, проверить HTTP 200, затем URL/защищённый API. При ошибке записывать только status и разрешённый code, без payload, cookie, token, password или полного error-context формы.
4. Foundation/journey/login/logout, negative/security проверки и реальные UI-входы, создающие кэш, сохраняются. Не делать forged session, очистку live buckets, IP rotation, sleeps для «зелёного» окна или повышение rate limits/timeouts.

В стандартной последовательности валидного кэша это уберёт четыре повторных входа: наблюдаемый бюджет 22 → 18 (с VPS preflight — 19). Проверку числа запросов/валидности кэша следует подтвердить измерением после реализации; оценка здесь не является результатом ещё не написанного кода.

Разделять БД по runtime можно обсудить как дальнейшую изоляцию, но это не минимальный фикс: 21 вход за минуту внутри одного runtime всё равно превысит лимит. Сброс buckets между тестами скрыл бы реальную защиту и не предлагается.

### Предложение B: готовность формы занятия

Оставить SSR-поля/отправку недоступными до готовности клиентских обработчиков (например, fieldset с disabled и явный сигнал готовности), затем сохранить текущие серверные и native проверки. Добавить детерминированный сценарий задержанных JS chunks: до готовности отправка невозможна; после готовности `31.02.2026` отклоняется, ввод сохраняется, POST отсутствует. Исходную проверку validationMessage и invalidWrites не убирать/не заменять более слабой.

Оба предложения **не внесены**: владелец разрешил сейчас мобильную правку и диагностику, а изменения auth/security и тестовой инфраструктуры потребовал предварительно согласовать. Production auth/security менять для A не требуется. Сам PR остаётся Draft, Production NO-GO сохраняется.
