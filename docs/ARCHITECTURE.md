# Architecture Handoff v2

Источник: [Issue #7](https://github.com/bam-low/mgimo/issues/7), включая **Architecture Review — уточнения владельца от 04.11.2026**, имеющие приоритет над ранними предварительными формулировками. Связанные документы: [PRD](PRD.md), [DECISIONS](DECISIONS.md), [DESIGN](DESIGN.md). Статусы: **APPROVED** — явно утверждено владельцем; **PROPOSED** — техническое предложение для ревью; **OPEN** — решение отсутствует. Документ не разрешает создавать приложение, схемы Prisma, миграции, зависимости или инфраструктуру.

## 1. Утверждённый контур и границы

**APPROVED:** модульный монолит; Next.js App Router, React, TypeScript, Tailwind CSS, PostgreSQL, Prisma, Zod, Vitest, Playwright. Версии, Node.js, менеджер пакетов, размещение и конкретная библиотека авторизации — **OPEN**. Ранее предварительный стек теперь утверждён как набор технологий, а не как совместимая конфигурация версий.

**PROPOSED:** внутренние модули Identity/Sessions, UniversityStructure, Enrollment, Schedule, AcademicRecords, Applications и Notifications; серверные сценарии координируют операции через одну транзакционную БД. Это границы ответственности, не микросервисы и не утверждённая структура каталогов/API. Клиентские UI и проверки Zod на клиенте не являются границей безопасности.

| В MVP — APPROVED | Только будущее / future-ready |
| --- | --- |
| Один заранее подготовленный вымышленный вуз; один студенческий университетский контекст | Несколько вузов у User, полноценная мультиарендность |
| Минимум два подтверждённых разных демо-студента и **один** демонстрационный STAFF | Несколько сотрудников, индивидуальные ACL/должности и стресс-сценарии решений разных сотрудников |
| Открытая регистрация; ручное подтверждение прикрепления; отказ и новая подача с историей | Создание вуза после одобрения платформой; приглашения/выдача STAFF отдельной процедурой; SSO |
| Перевод только сотрудником, отзыв подтверждённого группового прикрепления, аудит | Полное управление UniversityMembership: отдельный отзыв REVOKED, сложные жизненные циклы переводов/членств |
| Две роли, групповой график, read-only успеваемость, заявки/уведомления | Универсальная SaaS-панель и редактирование успеваемости не добавляются в MVP |

Вузы и STAFF подготавливаются только доверенным механизмом данных, не публичным UI. Все STAFF одного демо-вузa имеют право подтверждения, перевода и отзыва; в MVP аккаунт один, индивидуальная ACL не нужна. Публичная регистрация не принимает роль STAFF и не создаёт вуз. Демо-seed исключительно синтетический, однако пользователь регистрации вправе ввести собственные реальные данные. Требование вымышленных данных в дизайн-референсах/демо не означает синтетичность всех вводимых пользователями данных. Юридическое сопровождение вне scope команды; обязательные технические меры защиты этим не отменяются.

## 2. Контракт сущностей — APPROVED

Это описание связей и ответственности, не Prisma schema. Статусы в строках — доменные состояния, не отметки утверждения документа.

| Сущность | Контракт / контекст |
| --- | --- |
| User | Глобальная учётная запись: email, passwordHash, состояние аккаунта. **Глобального role нет**. Существование записи не даёт учебного доступа. |
| University | Имя, IANA timezone, статус; один экземпляр в MVP. |
| UniversityMembership | userId, universityId, role STUDENT/STAFF, status PENDING/APPROVED/REJECTED, timestamps/version; unique(userId, universityId). REVOKED — отдельный будущий отзыв членства, не синоним отзыва группы. |
| Faculty → Program → StudentGroup | Faculty принадлежит University; Program — Faculty; StudentGroup — Program. Вуз группы выводится через проверенную сервером иерархию; учитывается активность группы. |
| StudentProfile | Профиль студента в университетском контексте, связан с его членством; запись сама по себе не предоставляет права. Перечень разрешённых полей OPEN. |
| EnrollmentRequest | membershipId, targetGroupId, status PENDING/APPROVED/REJECTED, инициатор, решение/комментарий, timestamps/version. Все попытки сохраняются; не является обычной Application. |
| GroupMembership (Enrollment) | Подтверждённое прикрепление membership к группе; startedAt/endedAt/revokedAt, источник подтверждения, история. Максимум одно действующее прикрепление на членство в MVP. |
| EnrollmentAuditEvent | Неизменяемое событие создания, одобрения, отклонения, новой подачи, перевода или отзыва; актор, время и контекст результата. При переводе — причина, старая/новая группы. |
| Session | Серверная отзываемая сессия User; активность сессии не заменяет текущие проверки членства/прикрепления. Точный формат и библиотека OPEN. |
| Subject | Дисциплина в университетском контексте; модель периодов и привязки к программам OPEN. |
| ScheduleEntry | Занятие группы и дисциплины в контексте вуза; время/место. Не копируется в User или StudentProfile. |
| Grade | Собственная оценка/зачёт студента в контексте UniversityMembership и Subject. Не привязывать только к текущей группе: история переживает перевод. В MVP read-only. |
| Application | Обычная учебная заявка студента в контексте его UniversityMembership; отдельна от EnrollmentRequest. Типы/переходы OPEN. Личная история сохраняется после перевода. |
| ApplicationEvent | События изменения обычной Application с актором/временем, в её университетском контексте. Конкретная детализация OPEN. |
| Notification | Получатель и однозначный университетский контекст, связь с событием при наличии. Не смешивать данные разных членств будущего User; каналы/триггеры OPEN, кроме уведомления о подтверждении. |

**PROPOSED:** хранить явный membershipId для личных профилей/оценок/заявок/уведомлений, проверяя контекст связанной дисциплины/группы/события; не дублировать universityId без проверки согласованности. Точная физическая схема и ключи **OPEN**. Исторический groupId может сохранять происхождение записи, но не определяет единственное право на личную историю.

## 3. Инварианты и гарантии

**APPROVED:** один UniversityMembership на пару user/university, не более одного PENDING EnrollmentRequest на членство, не более одного активного GroupMembership в MVP. До подтверждения действующего прикрепления нет. Для членства, запроса, группы и сотрудника-решающего должен совпадать university scope. История не удаляется каскадом. Самоназначение STAFF запрещено.

| Гарантия | Где обеспечивать | Статус конкретного механизма |
| --- | --- | --- |
| Нет дубля учётной записи при повторной регистрации | Серверная нормализация/валидация и уникальность идентификатора входа в БД, атомарное создание связанных записей | Обязательный результат APPROVED; правила нормализации email и ключ повторной отправки PROPOSED/OPEN |
| unique(userId, universityId) | Уникальное ограничение БД | APPROVED контракт |
| Один PENDING и одно действующее прикрепление | Ограничения БД + транзакции, а не только предварительное чтение в сервере | APPROVED результат; PROPOSED частичные уникальные индексы PostgreSQL по membershipId с предикатами PENDING и endedAt/revokedAt отсутствуют |
| Согласованность вузов/иерархии/состояний | Сервер проверяет связи и переход, БД обеспечивает ссылочную целостность; PROPOSED дополнительные составные ключи там, где нужны | Поведение APPROVED; физические ограничения OPEN |
| Одобрение/перевод/отзыв не оставляют половинчатых состояний | Единая транзакция данных, статусов, прикреплений, аудита; подтверждение включает уведомление | APPROVED; PROPOSED транзакционная запись Notification, внешний канал при появлении — отдельное решение |
| Повторное решение не создаёт дубль | Проверка ожидаемого статуса/version, ограничения уникальности и идемпотентный результат либо безопасный отказ | APPROVED; конкретный протокол повторов PROPOSED |
| Сохранность истории | Нет каскадного удаления запросов, прежних прикреплений/личной истории/аудита; контролируемые серверные операции | APPROVED; сроки хранения и допустимое удаление профиля OPEN |

**PROPOSED:** в транзакции повторно читать состояние/активность группы, выполнять условное изменение ожидаемого статуса/version и отклонять конфликт. Уникальные ограничения — последняя защита; предварительный read сам по себе недостаточен. Откат при ошибке не оставляет активного прикрепления без решения/аудита. Если группа деактивирована во время PENDING, одобрение запрещено, запрос остаётся доступен уполномоченному сотруднику для последующего допустимого решения, без автоматического перевода в другую группу.

В MVP обязательна устойчивость к двойному клику, повторному HTTP-запросу/отправке и сбою одного сотрудника. Блокировки, уровень изоляции и версии для сложных гонок **между разными сотрудниками** — future-ready PROPOSED/OPEN, не обязательный multi-staff E2E конкурсного MVP.

## 4. Переходы и атомарность

Все изменения выполняются только после серверной проверки полномочий/контекста. Исторические записи не переписываются для имитации нового события.

| Операция | Предусловие | Атомарный результат / история | Статус |
| --- | --- | --- | --- |
| Первичная регистрация/подача | Валидная активная выбранная цепочка University → Faculty → Program → StudentGroup, допустимые минимальные данные | User + UniversityMembership(STUDENT,PENDING) + StudentProfile + EnrollmentRequest(PENDING); **без GroupMembership**, событие аудита | APPROVED |
| Одобрение | APPROVED STAFF того же вуза, ожидающий запрос, группа активна, нет действующего прикрепления | EnrollmentRequest APPROVED, членство PENDING → APPROVED, действующее GroupMembership, аудит и Notification в одной транзакции | APPROVED |
| Отказ | STAFF того же вуза, запрос PENDING | Запрос REJECTED, причина/аудит; при отсутствии прежнего подтверждения членство PENDING → REJECTED; активной группы нет | APPROVED; обработка иных будущих исторических контекстов OPEN |
| Новая подача после REJECTED | Тот же User и **тот же UniversityMembership**, нет другого PENDING; группа валидна | Новый EnrollmentRequest(PENDING), членство снова PENDING, прежние REJECTED неизменны, аудит | APPROVED |
| Перевод сотрудником | APPROVED STAFF и студент того же вуза с APPROVED членством/активным прикреплением, другая допустимая группа | Закрыть старое, открыть новое прикрепление атомарно; членство остаётся APPROVED. Аудит: инициатор, время, причина, прежняя/новая группа. Нет периода двойного доступа | APPROVED поведение; контракт операции PROPOSED ниже |
| Перевод в ту же группу | Текущая группа совпадает с целевой | Отказ/no-op, без дублирующего прикрепления | APPROVED; точный ответ PROPOSED |
| Отзыв подтверждённого прикрепления | APPROVED STAFF того же вуза, действующее GroupMembership | Завершить/отозвать GroupMembership, сохранить историю, согласованный аудит; новые защищённые серверные доступы прекращаются после фиксации. Исторический EnrollmentRequest остаётся APPROVED | APPROVED; состояние UniversityMembership и новая подача после отзыва ещё не утверждены |
| Отзыв UniversityMembership | Отдельная будущая операция | REVOKED на уровне вузовского членства; не выполнять автоматически при отзыве группы | Future-only; полный жизненный цикл OPEN |

**PROPOSED — перевод:** выбрать отдельную штатную серверную операцию сотрудника, без типа STAFF_TRANSFER и **без фиктивного EnrollmentRequest от студента**. Источник нового GroupMembership — эта операция и событие аудита, а не новый пользовательский запрос. Повтор уже завершённой операции возвращает сохранённый результат либо безопасно отклоняется; конкретный контракт/ключ идемпотентности OPEN.

**PROPOSED — после отзыва только группы:** оставить UniversityMembership=APPROVED, показывать отдельное производное состояние «прикрепление отозвано», учебный доступ закрыт; повторная подача допускается только по разрешению/действию сотрудника. Это однозначный вариант для ревью, **не утверждённое продуктовое поведение**. До его согласования нельзя автоматически открывать повторную подачу, сбрасывать членство в PENDING/REJECTED или менять историческое одобрение запроса. **OPEN:** процедура разрешения новой подачи и последующее состояние членства.

После перевода закрытые ресурсы прежней группы недоступны на новых запросах; собственные оценки и личные заявки сохраняются в контексте членства и доступны при выполнении текущих правил доступа. Старый groupId не является обходом проверки. После отзыва группы личная история сохраняется в БД, но её учебное чтение блокируется до восстановления разрешённого доступа.

## 5. Матрица серверного доступа — APPROVED

Для каждого защищённого действия проверяются **session active + User active + UniversityMembership(role/status) + university scope + активное GroupMembership, где необходимо + ownership/scope конкретного объекта + допустимый переход**. Deny by default. Роль или статус из клиента и cookie-кэш прав не являются доказательством. APPROVED членство без действующего прикрепления не открывает расписание, успеваемость или учебные заявки.

| Контекст | Вход / разрешённый собственный профиль | Свой запрос прикрепления / выбранная группа | Закрытое расписание | Собственные оценки / обычные заявки | Уведомления | Действия STAFF |
| --- | --- | --- | --- | --- | --- | --- |
| Неаутентифицирован / сессия отозвана / User отключён | Защищённое чтение запрещено; публичная регистрация/вход только при допустимом аккаунте | Нет | Нет | Нет | Нет | Нет |
| STUDENT PENDING | Вход, минимальный собственный профиль | Свой статус и выбранная группа; без закрытых ресурсов группы | Нет | Нет | Только собственный безопасный результат прикрепления; состав DTO PROPOSED | Нет |
| STUDENT REJECTED | Вход, минимальный собственный профиль | Свой результат/история и новая подача без второго PENDING | Нет | Нет | Только безопасный результат прикрепления; DTO PROPOSED | Нет |
| STUDENT APPROVED + активная группа | Свой профиль | Свой статус/история, без самостоятельного перевода | Только своя действующая группа | Только свои записи данного членства, read-only оценки; заявки в разрешённых переходах | Только свои в данном вузе | Нет |
| APPROVED STAFF своего вуза | Свой профиль | Рассмотрение, подтверждение/отказ; перевод/отзыв по правилам | Управление групповым расписанием своего вуза | Обработка заявок своего вуза; нет произвольного доступа к чужой успеваемости | Только разрешённые данные по роли/получателю | Управление структурой, прикреплениями, расписанием и заявками своего вуза |
| Прикрепление отозвано, даже при APPROVED членстве | Вход, минимальный собственный профиль | Свой исторический результат остаётся; новая подача OPEN/PROPOSED, не автоматически | Нет | Нет; история хранится | Только собственное безопасное сообщение о состоянии; DTO PROPOSED | Нет |

Доступ к уведомлению не должен косвенно раскрывать закрытое расписание/оценки/заявку; личные сообщения проверяются по получателю и контексту. Университетское REVOKED (будущий механизм) не даёт учебных прав. STAFF не нуждается в студенческом прикреплении для собственных штатных действий, но его членство/роль/вуз и объект всё равно проверяются. Успеваемость в MVP read-only; отдельная выдача сотруднику права редактирования не утверждена.

## 6. Публичные данные, сессии и безопасность

**APPROVED:** открытая регистрация с собственными данными остаётся; seed/демо-скриншоты синтетические. Минимизировать поля. Не помещать профили, заявки, токены и секреты в публичные URL, логи, общие кэши, Git или client bundle. Возвращать минимальные DTO, изолировать студентов и вузовские контексты. Повторная регистрация не создаёт дублей; ошибки не раскрывают лишние сведения о чужих аккаунтах. Точный текст ответов и способы защиты от enumeration **PROPOSED/OPEN**.

**APPROVED:** Argon2id либо обоснованный эквивалент, серверные отзываемые сессии; secure HttpOnly SameSite cookies в production, HTTPS; защита CSRF/XSS, CSP, серверная валидация Zod, rate limits, секреты вне Git, безопасные резервные копии. Библиотеку авторизации **не выбирать без проверки совместимости credentials и режима database sessions**. Точные алгоритмические параметры, значения cookie/CSP, лимиты, TTL/продление и отзыв сессий, библиотека и процесс резервного восстановления — **OPEN**; сейчас ничего не устанавливается и инфраструктура не меняется.

Личные ответы не выдаются из общего кэша. **PROPOSED:** private/no-store для защищённых HTTP-ответов и запрет общего серверного кэширования персональных DTO; конкретные настройки Next.js/HTTP проверяются после выбора версий. При смене аккаунта, переводе или отзыве актуализировать контекст и очищать прежнее приватное клиентское состояние. После фиксации отзыва новые защищённые серверные запросы (включая ранее открытую сессию) должны сразу отказать, без ожидания истечения сессии/кэшированного APPROVED. Уже просмотренную/сохранённую пользователем информацию дистанционно стереть невозможно; протокол синхронизации интерфейса **OPEN**, это не обещание удаления чужих сохранённых копий.

## 7. Сохраняемые продуктовые и временные требования

**APPROVED:** студенту — профиль, сегодня/неделя, оценки/зачёты read-only, личные заявки/статусы, уведомления; сотруднику — Faculty/Program/StudentGroup, групповое расписание, прикрепления и обычные заявки. ScheduleEntry принадлежит группе, не копируется в профиль; учебный доступ возможен только после подтверждения и при действующем прикреплении.

Главная показывает все занятия дня, выделяет реальную текущую пару, локально обновляет её прогресс 0–100% с текстовым эквивалентом. Состояния: до пар, перемена, текущая пара, всё закончилось, занятий нет. Вуз имеет IANA timezone; нельзя молча использовать зону браузера/хоста. **PROPOSED:** конкретные моменты UTC, отображение/календарный день в зоне вуза, интервал пары [начало, конец). **OPEN:** конкретная зона, повторы/исключения, пересечения, частота обновления и синхронизация часов. Локальный расчёт прогресса не заменяет серверные права на получение расписания.

Academic Editorial, направление логотипа B, 360/390 CSS px и два исходных PNG сохраняются по [DESIGN](DESIGN.md); финальный SVG/числовые токены не утверждаются архитектурой. Прототип и все ресурсы доступны из РФ без VPN; **PROPOSED:** минимизировать внешние загрузки и рассмотреть локальные шрифты после проверки лицензий. Площадка/метод проверки из РФ **OPEN**. Встроенного GPT/ИИ-помощника и multi-tenant SaaS в MVP нет; маркировка «концепт, не официальный сервис» обязательна.

## 8. Будущие проверки реализации — не выполняются в Issue #7

Стек тестов Vitest/integration/Playwright утверждён; конкретное распределение ниже **PROPOSED**, ожидаемое поведение — APPROVED. Никакие тестовые исходники сейчас не создаются.

| Уровень | Обязательные сценарии будущего MVP |
| --- | --- |
| Vitest / серверные правила | PENDING/REJECTED/отозванное прикрепление не дают учебных прав, APPROVED без активной группы недостаточно; входная роль STAFF отклоняется; проверки ownership/university/group; состояние расписания/прогресс/зона |
| Integration с БД | Регистрация атомарна и не дублируется; REJECTED → новый запрос на том же членстве с историей; максимум один PENDING; двойное подтверждение/повтор HTTP не создают дубль группы/аудита результата; сбой откатывает связанные изменения |
| Integration прикреплений | Деактивированная во время PENDING группа не одобряется; перевод только STAFF, атомарно, без двух групп; перевод в ту же группу — отказ/no-op; прежняя группа закрыта, собственные оценки/заявки сохраняются; отзыв группы не меняет APPROVED запроса; сессия после отзыва не даёт нового учебного доступа |
| Playwright / прямые HTTP | Неавторизованный запрос, отозванная сессия/отключённый User отклоняются; PENDING/REJECTED не читают расписание/оценки/заявки даже с известными id; чужой вуз/группа/личные записи недоступны; нельзя зарегистрировать STAFF |
| Playwright / кэши и роли | Два подтверждённых разных студента и один сотрудник; смена аккаунта не раскрывает предыдущие данные; после перевода/отзыва актуализированная UI не показывает устаревшие приватные данные; старая сессия не обходит отзыв; read-only успеваемость |

Проверки будущего второго вуза и стресс-конкуренция разных сотрудников — future-ready, не обязательное E2E MVP. В текущем Issue проверяются лишь документы: `python3 scripts/check_docs.py`, `git diff --check`, Documentation CI на HEAD Draft PR. Зелёная документационная проверка не доказывает работоспособность регистрации или защиты данных.

## 9. OPEN / PROPOSED перед реализацией

- PROPOSED: APPROVED членство после отзыва группы, отдельное отображаемое состояние и новая подача только по действию сотрудника; требуется продуктовое подтверждение.
- PROPOSED: отдельная операция сотруднического перевода, без STAFF_TRANSFER/фиктивного студенческого запроса; утвердить контракт повторов.
- OPEN: версии стека/Node.js/пакетный менеджер, библиотека auth с проверкой credentials + database sessions, TTL/лимиты/параметры защиты, физические ограничения БД и стратегия транзакций.
- OPEN: минимальные поля профиля/DTO для состояний без группы, подтверждение email/восстановление, правила хранения и удаления личных данных/аудита без потери истории.
- OPEN: конкретная IANA-зона/структура вуза, шкалы/периоды/источник read-only оценок, типы обычных заявок/уведомлений, семантика повторов/пересечений расписания, синхронизация клиентского состояния.
- Future OPEN: несколько вузов/SSO/выдача STAFF и полный отзыв университетского членства; точная модель периодов/академических переводов между вузами. Не переносить в scope MVP.
